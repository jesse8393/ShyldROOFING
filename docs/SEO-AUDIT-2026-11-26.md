## Scope and method

* **Crawl.** `scripts/audit/seo_crawl.py` fetched all 60 sitemap URLs, followed every internal link, and fetched all
  246 referenced assets. `scripts/audit/seo_analyze.py` produced `docs/seo-audit-2026-11-26/onpage-crawl.md` (per page
  table). `scripts/audit/mirror.py` saved the same files locally and also fetched the two module scripts that the page
  scripts import (`inquiry-form.*.js` and `attribution.*.js`), which no page references directly.
* **Lighthouse 12.8.2** driving the Chromium 158 build that Playwright installed in the sandbox (Lighthouse ships no
  browser; the path is hard coded as `chromePath` in `scripts/audit/lighthouse-mirror.mjs`), default mobile emulation
  (412 by 823 CSS pixels at a device pixel ratio of 1.75) and simulated throttling. The sandbox browser cannot complete
  TLS to outside hosts, so Lighthouse ran against a byte for byte local mirror of the live files (served with
  `http-server -e html`, host name mapped to 127.0.0.1). Two audits that cannot pass on a plain HTTP mirror were skipped
  and verified with curl on the live server instead: `is-on-https` (live: HTTPS with HTTP Strict Transport Security,
  HSTS) and `redirects-http` (live: `http://` returns 301 to `https://`). The Google tag loader was pointed at an empty
  local stub so the mirror did not call out; the consequences for the scores are stated under Lighthouse results.
  Zero weight diagnostics about text compression, HTTP/2 and back/forward cache describe the mirror server, not the
  live server; live responses use Brotli, HTTP/2 with HTTP/3 advertised, and `Cache-Control: no-cache` on HTML.
* **PageSpeed Insights API** was attempted for real Chrome field data (CrUX) and returned HTTP 429 (keyless daily quota
  exhausted). No field data is included. Run https://pagespeed.web.dev/ manually for CrUX.
* **Indexing.** Google search blocked automated queries (JavaScript challenge, then the session's permission layer
  denied a second attempt). Search Console API access is not configured for this session. Bing was queried with `site:`
  and brand terms alongside four control domains; the responses are tabulated in
  `docs/seo-audit-2026-11-26/bing-queries.md`. The jesse@parkerconstructioncompany.com inbox was searched, with no date
  limit, for Search Console, Google Business Profile and Bing mail about the business.
* **Source comparison.** Every branch of this repository was fetched and the newest one (`claude/jakarta-preview`,
  ab3af27, pushed 2026-10-07) was built and compared file by file with the live server.

Note on `lastmod`: all 60 URLs carry the same date, 2026-10-08. Google ignores `lastmod` when it does not reflect real
change dates. The sitemap generator in `src/pages/sitemap.xml.ts` reads a date from a hand maintained list
(`contentDates` in `src/data/business.ts`, 16 entries) for the 16 non city routes and gives every `/roofing-*` city page
the `/service-areas` date, so even a rebuild from the repository stamps all city pages with one date. Real per page
dates need a date for each city page, kept up to date on every edit, or a generator that reads each page's last commit
date from git.

Note on scripts: `public/.htaccess` sets a one year expiry for `application/javascript` and `text/javascript`, but the
live server labels the script files `application/x-javascript`, a type the rules do not name, so they fall back to the
host's seven day default. The `<FilesMatch "^assets/...">` rule meant to add `immutable` to hashed assets can never
match, because `FilesMatch` sees file names, not paths; only the font rule works. Harmless, but one year would match the
rest.

Reading the Lighthouse columns: the performance numbers are lab numbers against a local server, so they understate
real world time to first byte. They were also measured with the Google tag loader replaced by an empty stub, so the
script the live pages load from Google (183 KB compressed, 546 KB uncompressed on 2026-11-26) and its follow up
requests are not in the Performance, Best Practices, main thread or third party audits. Live Performance will be
somewhat lower than 97 to 100, and the Best Practices 100 is confirmed for the site's own code, not for the Google
script. The numbers are useful for relative comparison and for the diagnostics, not as a substitute for CrUX field
data. Real improvements Lighthouse pointed at (all zero weight in the score):

* Home hero image: the image delivery insight reports 41 KiB of waste on the 740 pixel portrait AVIF shown in a
  375 CSS pixel slot, but that insight ignores the emulated 1.75 device pixel ratio. The slot needs 656 device pixels,
  so 740w is the correct pick from the 480w, 640w and 740w candidates, and a tighter `sizes` value would change
  nothing; the device pixel ratio aware `uses-responsive-images` audit did not flag it. A candidate near 656 pixels
  would save roughly 12 KiB by pixel area. Low value.
* Service and project card images are larger than their slots. The device pixel ratio aware audit estimates 13 to
  16 KiB saved per image; the image delivery insight's 23 to 27 KiB ignores device pixel ratio.
* Inlined CSS: about 10 to 11 KiB of the 24 to 28 KiB inlined on a typical page is unused (10.6 of 26.2 KiB on each
  city page) and 14 of 33 KiB on the home page. Every page inlines one style block, the global stylesheet plus the
  styles of the components it uses. This is a deliberate trade off that removes a render blocking request; leave it
  unless pages grow.
* Forced reflow flagged on 7 pages (home, metal roofing, and the Cookeville, Hermitage, Mt. Juliet, Murfreesboro and
  Spring Hill city pages): an inline script reads layout after writing it. Minor.

Improvements, none of them errors:

* No `sameAs`. Add the Google Business Profile URL (once the profile is verified) and any real social profiles to the
  business node. In our judgement this is the most useful addition in this list, because it ties the schema entity to
  the profile Google already holds for the business; schema is not a direct ranking factor.
* `Article.author` is the organisation. A `Person` node for the owner (name, `jobTitle`, `worksFor`, `sameAs`) on the
  About page and as the article author strengthens experience and expertise signals.
* `Article.image` is the generic Open Graph image on both guides. Use a page specific image.
* No `aggregateRating`. Correct: do not add one until real reviews exist, and then only with the real count.
* The FAQ sections have no `FAQPage` markup. Google restricted FAQ rich results to government and health sites in
  2023, so adding it brings no Google benefit; it can help AI assistants quote the answers. Optional.
* `geo` has four decimal places (about 10 metres). Fine for a service area business that does not publish a street
  address.

## Reproducing this audit

```
# crawl and on page analysis (needs only python3 and curl)
curl -sS https://shyldroofing.com/sitemap.xml | grep -o '<loc>[^<]*</loc>' | sed 's/<\/\?loc>//g' > /tmp/sitemap-urls.txt
python3 -I scripts/audit/seo_crawl.py /tmp/audit /tmp/sitemap-urls.txt
python3 -I scripts/audit/seo_analyze.py /tmp/audit/crawl.json > /tmp/audit/onpage-summary.md

# local mirror, Lighthouse and city page overlap (needs node, lighthouse, chrome-launcher, http-server and a Chrome binary)
python3 -I scripts/audit/mirror.py /tmp              # writes /tmp/mirror from /tmp/audit/crawl.json, including imported modules
http-server /tmp/mirror -p 80 -a 127.0.0.1 -e html -s &
node scripts/audit/lighthouse-mirror.mjs /tmp       # reads /tmp/sitemap-urls.txt, writes /tmp/lh/; set chromePath for your machine
python3 -I scripts/audit/lh_summary.py /tmp/lh/summary.json > /tmp/lh/lighthouse.md
python3 -I scripts/audit/city_overlap.py /tmp/mirror > /tmp/city-overlap.md
```

Lighthouse against the live site directly (`npx lighthouse https://shyldroofing.com/`) is the better choice on any
machine that can reach the internet normally; the mirror exists only because this sandbox cannot.
